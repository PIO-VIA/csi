===============================================================================
DIAGNOSTIC : Erreur lors de la création d'une consultation (espace Médecin)
Projet : CSI Sécurité Sociale
Workflow attendu :
  Médecin crée une consultation
    -> (optionnel) génère une feuille de maladie
       -> la feuille déclenche AUTOMATIQUEMENT un remboursement EN_ATTENTE
          -> le remboursement apparaît dans l'espace Agent ("non remboursés")
             -> l'agent confirme (mode de paiement) -> statut EFFECTUE
===============================================================================

RÉSUMÉ DU PROBLÈME
-------------------
En analysant le code (frontend Next.js + backend Spring Boot) et la capture
DevTools fournie, plusieurs bugs distincts s'enchaînent et cassent le
parcours "création de consultation" côté médecin. Ce ne sont pas des bugs
réseau/serveur isolés : ce sont des incohérences de logique entre le
frontend (lib/api.ts, lib2/*) et le backend (Controllers/Services Spring).

Les erreurs visibles dans la console (400 sur /generaliste/{id}, 404 sur
/remboursements/{id}, "Bad Request" répétés) sont les symptômes de 4 bugs
précis détaillés ci-dessous, classés par impact.

===============================================================================
PARTIE 1 — MODIFICATIONS FRONTEND (Next.js)
===============================================================================

--- BUG FRONT #1 (CRITIQUE) — la page "Nouvelle consultation" ne distingue
    pas Généraliste / Spécialiste ---

Fichier : app/(dashboard)/medecin/consultations/nouvelle/page.tsx

Le payload envoyé est toujours construit ainsi, peu importe le rôle réel
du médecin connecté :

    const payload = {
      assureId: Number(data.assureId),
      generalisteId: user.id,   // <-- TOUJOURS user.id, même si SPECIALISTE
      ...
    };

Or côté backend, ConsultationServiceImpl.creerConsultation() fait :

    Generaliste generaliste = generalisteRepository.findById(dto.getGeneralisteId())
        .orElseThrow(() -> new IllegalArgumentException(...));

La table `generaliste` est une sous-table d'héritage JOINED distincte de
`specialiste`. Si le médecin connecté est un SPECIALISTE, son id n'existe
PAS dans `generalisteRepository` -> IllegalArgumentException -> HTTP 400
"Bad Request". C'est exactement le type d'erreur vu dans la capture.

De plus, sur cette même page, getMesAssures() appelle
/api/medecins/me/assures, qui côté backend fait :

    generalisteRepository.findByEmail(email)
        .orElseThrow(() -> new ResourceNotFoundException(
            "Aucun médecin généraliste trouvé pour le compte connecté"));

Donc un Spécialiste connecté reçoit une 404 silencieuse (catchée dans le
.catch() de la page -> liste de patients vide), puis si jamais il force
quand même l'envoi du formulaire, ça part en 400 côté création.

FIX :
1. Restreindre l'accès à "Nouvelle consultation" aux médecins de type
   GENERALISTE uniquement (vérifier user.role === 'GENERALISTE' au
   montage de la page, rediriger sinon vers /medecin avec un message
   explicite "Seul le médecin traitant peut créer une consultation").
2. Dans components/ui/Sidebar.tsx, le lien "Nouvelle consultation"
   (compose button, MEDECIN_NAV) est affiché pour GENERALISTE ET
   SPECIALISTE. Le conditionner à role === 'GENERALISTE'.
3. Documenter clairement (commentaire + toast) : un Spécialiste intervient
   uniquement via une PrescriptionConsultation (orientation), jamais en
   créant directement une Consultation.

--- BUG FRONT #2 (IMPORTANT) — mauvais ID utilisé pour récupérer un
    remboursement (cause les 404 "remboursements/9") ---

Fichier : lib/api.ts — fonctions loadFeuilles(), getFeuillesByAssure(),
getMesFeuilles()

Le code fait, pour chaque feuille remboursée :

    const remb = await RemboursementsService.getById5(feuille.id);

Mais RemboursementsService.getById5(id) appelle GET /api/remboursements/{id}
qui attend l'ID PROPRE du Remboursement (sa colonne `id` dans la table
`remboursement`), pas l'ID de la FeuillemMaladie. Ce sont deux séquences
d'auto-incrément INDÉPENDANTES (table feuille_maladie vs table
remboursement). Dès qu'elles divergent un peu (suppression de test, ordre
de création différent, etc.), l'appel renvoie 404 — ce qui correspond aux
erreurs "remboursements/9 ... 404" vues dans la capture.

FIX (recommandé, le plus simple) :
Le backend renvoie DÉJÀ le montant remboursé dans la réponse de
GET /api/feuilles-maladie (et /assure/{id}, /medecin/me) via le champ
FeuillemMaladieResponseDTO.montantRembourse. Il n'y a donc AUCUN besoin
d'un second appel réseau.

  a) Dans lib/mappers.ts, mapFeuille() : lire raw.montantRembourse et
     raw.assureNom / raw.consultationDate déjà renvoyés par le backend
     au lieu de les ignorer.
  b) Dans types/index.ts, ajouter un champ optionnel `montantRembourse?:
     number` (et éventuellement `dateRemboursement?`, `modePaiement?` si
     vous enrichissez aussi le DTO backend, voir Partie 2).
  c) Dans lib/api.ts, supprimer complètement les appels
     RemboursementsService.getById5(feuille.id) dans loadFeuilles(),
     getFeuillesByAssure() et getMesFeuilles() : ils sont inutiles, lents
     (1 requête HTTP par feuille) et buggés.

--- BUG FRONT #3 (IMPORTANT) — chargement de TOUTES les consultations
    interroge l'endpoint "généraliste" même pour les spécialistes ---

Fichier : lib/api.ts — fonction loadAllConsultations()

    const medecins = await loadMedecins();
    const results = await Promise.all(
      medecins.map(async (m) => {
        try {
          return await ConsultationsService.getByGeneraliste(m.id);
        } catch (err) {
          console.error(`Error fetching consultations for doctor ID ${m.id}:`, err);
          return [];
        }
      }),
    );

Cette fonction boucle sur TOUS les médecins (généralistes + spécialistes)
et appelle /api/consultations/generaliste/{id} pour chacun. Pour un
spécialiste, ConsultationServiceImpl.getConsultationsByGeneraliste()
lève une IllegalArgumentException (400) car
generalisteRepository.existsById(specialisteId) est faux. D'où les
multiples "Failed to load resource ... generaliste/25, /30, /41 ...
status 400" et "Error fetching consultations for doctor ID 25/30/41"
visibles dans la capture — ce sont très probablement des IDs de
spécialistes.

FIX :
    const medecins = (await loadMedecins()).filter(m => m.type === 'GENERALISTE');

Ne boucler que sur les généralistes, puisque seuls eux peuvent être
rattachés à une consultation (cf. Partie 2, point sur le modèle de
données). Les erreurs disparaîtront immédiatement de la console.

--- BUG FRONT #4 (mineur, gêne le diagnostic) — message d'erreur générique
    masque la vraie cause ---

Fichier : app/(dashboard)/medecin/consultations/nouvelle/page.tsx

    } catch (e) {
      error(t('common.error'));
    }

Remplacer par :

    } catch (e) {
      error(getApiErrorMessage(e));
    }

(la fonction getApiErrorMessage existe déjà dans lib/api.ts et est déjà
utilisée ailleurs). Cela aurait permis de voir directement le message
backend réel ("Erreur: L'assure doit consulter son medecin traitant" ou
le 400 du généraliste introuvable) au lieu de devoir lire la console.

PARTIE 2 — MODIFICATIONS BACKEND (Spring Boot)
===============================================================================

--- BUG BACK #1 (CRITIQUE) — mauvais code HTTP sur l'erreur métier de
    création de consultation ---

Fichier : src/main/java/com/enspy/csi/service/impl/ConsultationServiceImpl.java

    if (assure.getMedecinTraitant() == null || !assure.getMedecinTraitant().getId().equals(generaliste.getId())){
        throw new IllegalStateException("Erreur: L'assure doit consulter son medecin traitant");
    }

Fichier : src/main/java/com/enspy/csi/exception/GlobalExceptionHandler.java

    @ExceptionHandler(IllegalStateException.class)
    public ResponseEntity<?> handleIllegalState(IllegalStateException ex) {
        return ResponseEntity.status(HttpStatus.INTERNAL_SERVER_ERROR).body(...) // 500 !
    }

Une erreur de RÈGLE MÉTIER (l'assuré n'a pas ce médecin comme médecin
traitant) est actuellement traduite en HTTP 500 "Internal Server Error"
au lieu d'un 400/409. Ça trompe le frontend (qui peut traiter différemment
un 4xx "attendu" d'un 5xx "panne serveur") et complique le debug.

FIX :
  a) Remplacer IllegalStateException par IllegalArgumentException dans
     creerConsultation() pour cette validation précise (ou créer une
     exception dédiée, ex. BusinessRuleException -> 409 CONFLICT).
  b) Dans GlobalExceptionHandler, ne garder handleIllegalState() (500)
     que pour de VRAIES erreurs serveur inattendues ; toute violation de
     règle métier doit remonter en 400 ou 409, jamais en 500.

--- BUG BACK #2 (IMPORTANT) — endpoint "consultations/generaliste/{id}"
    rejette les IDs de spécialistes sans message clair ---

Fichier : src/main/java/com/enspy/csi/service/impl/ConsultationServiceImpl.java

    public List<ConsultationResponseDTO> getConsultationsByGeneraliste(Long generalisteId) {
        if (!generalisteRepository.existsById(generalisteId)){
            throw new IllegalArgumentException("Généraliste dont l'id est " +generalisteId+ " introuvable" );
        }
        ...

Ce comportement est correct EN SOI (l'endpoint est conçu pour les
généralistes uniquement), mais rien ne l'indique côté documentation
Swagger/OpenAPI, et le frontend l'appelait pour tout le monde (corrigé
en Partie 1, bug #3). Confirmez juste qu'aucun autre endroit du code ne
réutilise cet endpoint pour un spécialiste.

FIX (optionnel mais propre) :
  Ajouter dans la doc Swagger (@Operation) une précision explicite :
  "Réservé aux médecins généralistes (médecin traitant)".

--- BUG BACK #3 (IMPORTANT) — aucun endpoint pour retrouver un
    Remboursement à partir de l'ID d'une FeuillemMaladie ---

Le repository expose déjà la méthode nécessaire :

    // RemboursementRepository.java
    Optional<Remboursement> findByFeuilleMaladieId(Long feuilleMaladieId);

...mais elle n'est utilisée QUE côté service interne
(RemboursementServiceImpl), jamais exposée via un Controller. Le frontend
a donc bricolé un appel incorrect vers GET /api/remboursements/{id} avec
le mauvais ID (cf Partie 1, bug #2).

FIX RECOMMANDÉ (le plus simple, pas de nouvel endpoint nécessaire) :
Le champ FeuillemMaladieResponseDTO.montantRembourse existe déjà et est
déjà rempli dans FeuillemMaladieServiceImpl.toDTO() :

    if (fm.getRemboursement() != null) {
        dto.setMontantRembourse(fm.getRemboursement().getMontant());
    }

-> Aucune modification backend n'est donc strictement nécessaire pour ce
   point : il suffit que le frontend exploite ce champ (Partie 1, bug #2).

FIX ALTERNATIF (si vous voulez quand même un endpoint dédié, par exemple
pour afficher la date de remboursement et le mode de paiement, absents du
DTO actuel) :
  a) Enrichir FeuillemMaladieResponseDTO avec dateRemboursement et
     modePaiement (déjà disponibles via fm.getRemboursement()), pour tout
     avoir en un seul appel — c'est la solution la plus cohérente avec
     l'architecture actuelle plutôt que multiplier les endpoints.
  b) OU ajouter un endpoint dédié dans RemboursementController :
        @GetMapping("/by-feuille/{feuilleMaladieId}")
        @PreAuthorize("hasRole('ORGANISME') or @securityService.isSelfAssureForFeuille(principal, #feuilleMaladieId)")
        public ResponseEntity<?> getByFeuille(@PathVariable Long feuilleMaladieId) {
            return ResponseEntity.ok(remboursementService.getByFeuilleMaladieId(feuilleMaladieId));
        }
     (nécessite d'ajouter la méthode correspondante dans
     RemboursementService/Impl basée sur findByFeuilleMaladieId).

--- AMÉLIORATION BACK #4 (mineure) — idFeuille jamais généré
    automatiquement ---

Fichier : src/main/java/com/enspy/csi/service/impl/FeuillemMaladieServiceImpl.java

    FeuillemMaladie fm = new FeuillemMaladie();
    fm.setIdFeuille(dto.getIdFeuille());   // souvent null car le frontend
                                            // ne l'envoie jamais (voir
                                            // lib/api.ts createConsultation)

Comme pour Assure.idAssure (généré via "ASS-" + UUID...), il serait plus
robuste de générer idFeuille côté serveur si non fourni :

    if (dto.getIdFeuille() == null || dto.getIdFeuille().isBlank()) {
        fm.setIdFeuille("FM-" + LocalDate.now().getYear() + "-"
            + UUID.randomUUID().toString().substring(0, 8).toUpperCase());
    } else {
        fm.setIdFeuille(dto.getIdFeuille());
    }

Ce n'est pas bloquant aujourd'hui (PostgreSQL autorise plusieurs valeurs
NULL dans une colonne UNIQUE), mais ça laisse toutes les feuilles sans
référence lisible dans l'UI agent/médecin/assuré, ce qui n'est pas
souhaitable pour un document officiel de sécurité sociale.

--- CONFIRMATION — la chaîne feuille -> remboursement -> validation agent
    est CORRECTE une fois les bugs ci-dessus corrigés ---

FeuillemMaladieServiceImpl.enregistrerFeuilleMaladie() appelle bien,
automatiquement et dans la même transaction :

    remboursementService.initierRemboursement(saved.getId());

qui crée un Remboursement au statut EN_ATTENTE. Côté agent,
GET /api/remboursements/non-rembourses (RemboursementController ->
feuillemMaladieService.getFeuillesNonRemboursees()) renvoie bien la liste
des feuilles non remboursées, affichée dans
app/(dashboard)/admin/remboursements/page.tsx. L'agent confirme ensuite
via PATCH /api/remboursements/{feuilleMaladieId}/confirmer?modePaiement=...
qui passe le statut à EFFECTUE et marque la feuille comme remboursée
(taux 100% généraliste / 80% si orientation spécialiste, calculé dans
RemboursementServiceImpl.calculerMontant()).

=> Ce flux backend N'A PAS BESOIN d'être réécrit. Le blocage actuel vient
   uniquement des bugs en amont (création de consultation qui échoue
   avant même d'atteindre la création de la feuille — Partie 1 bug #1 et
   Partie 2 bug #1), et des appels frontend mal formés qui polluent la
   console sans empêcher le flux principal (Partie 1 bugs #2 et #3).

ORDRE DE CORRECTION RECOMMANDÉ
===============================================================================
1. Frontend bug #1 (restreindre la page aux généralistes) — débloque
   immédiatement la création de consultation pour le bon rôle.
2. Backend bug #1 (code HTTP correct sur la validation métier) — pour que
   les futures erreurs légitimes soient lisibles et bien typées.
3. Frontend bug #3 (filtrer les généralistes dans loadAllConsultations) —
   nettoie la console et les listings admin/médecin.
4. Frontend bug #2 + utilisation de montantRembourse — supprime les 404
   et accélère le chargement des listes de feuilles/remboursements.
5. Frontend bug #4 (afficher le vrai message d'erreur) — pour accélérer
   les futurs diagnostics.
6. Backend amélioration #4 (génération auto de idFeuille) — qualité des
   données, non bloquant.
